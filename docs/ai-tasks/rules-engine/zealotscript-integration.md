# ZealotScript Integration

## How Lua content renders in the editor

Lua scripts interact with item content by writing **ZealotScript markdown** — the same format the `ZealotScriptSerializer` produces. The backend stores it as plain text in `item.content`. No special handling is needed at the API layer.

### Data flow

```
Lua script
  → zealot.items.update(id, { content = "# Title\n\nBody **text**" })
  → ItemService::update_item  (stores raw string in DB)
  → Browser fetches item via GET /item/id/:id
  → ZealotScriptEditor calls parseZealotScript(schema, item.content)
  → ProseMirror renders the document
```

### Content format

Lua-generated content must be valid ZealotScript — standard CommonMark with Zealot extensions:
- Headings: `# H1`, `## H2`, etc.
- Bold/italic: `**bold**`, `_italic_`
- Lists: `- item` (unordered), `1. item` (ordered)
- Tables: GFM pipe tables (`| col | col |`)
- Code blocks: fenced ` ``` `
- Admonitions: `!!! note\n    Body` (Zealot-specific)

Scripts should use `table.concat(lines, "\n")` to build content strings rather than string concatenation.

## Phase 1: Content generation rules

Lua rules write to `item.content` via `zealot.items.update`. This is already fully supported.

**Example — daily agenda item:**
```lua
local items = zealot.items.filter({{ key = "Date", op = "eq", value = zealot.date }})
local lines = { "# Agenda — " .. zealot.date, "" }
for _, item in ipairs(items) do
    table.insert(lines, "- " .. item.title)
end
zealot.items.update(agenda_id, { content = table.concat(lines, "\n") })
```

## Phase 2: `last_output` display in Rules screen

Every `zealot.notify(msg)` call appends `msg` to an in-memory buffer during execution. After the script finishes, the buffer is written to `rule.last_output` in the DB. The Rules screen fetches and displays this output after a "Run Now" call, giving the user feedback on what the rule did.

---

## Phase 3: Embedded rule output in items (future)

A future ZealotScript extension would support an inline "rule embed" block:

```
{{rule:my-rule-id}}
```

This block, when rendered, fetches `GET /rule/{id}/output` and injects the `last_output` text verbatim into the rendered document. The output is rendered as ZealotScript (parsed and displayed, not raw HTML).

**Use case:** A "Project Dashboard" item contains `{{rule:project-rollup}}`. Every time the rollup rule runs (e.g. cron daily), the item shows fresh computed data without the user editing anything.

**Implementation notes (deferred):**
- Add `GET /rule/{id}/output` endpoint returning `{ output: string | null }`
- Add `rule_embed` node type to ProseMirror schema (`TASK-ZS-001`)
- Parser recognises `{{rule:...}}` syntax
- `RuleEmbedNodeView` fetches output via `RuleAPI.GetOutput(id)` and renders it

## ZealotScript custom views (further future)

Lua could generate entire custom item-list views by populating a special item type `View`. A View item's content is a ZealotScript document generated by a rule. When the user navigates to `/item/title/My View`, they see the computed document.

This requires no new infrastructure beyond what's already planned — it's just a naming convention:

1. Create an item type `View` (one-time setup)
2. Write a rule that creates or updates an item of type `View` with generated ZealotScript content
3. Users navigate to the view item like any other item

This pattern works immediately in Phase 1 with no additional development.
